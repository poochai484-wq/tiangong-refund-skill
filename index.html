二、退费skill 流程图与角色权限

流程来源： 业管-退费skill梳理 —— 业管基于现有知识库梳理的退费流程，是 Skill 的原始需求基线。

把散落在知识库中的退费流程，收敛成两张图：流程图说明「怎么判」，角色权限表说明「谁能办、办多少、办不了找谁」。两者合起来就是一份可直接执行的 Skill。

2.1　退费 Skill 流程图

从「用户提出退费诉求」起，按订单类型分流，逐条判断条件后输出可退 / 不可退与对应处理方案

节点说明： 退费skill节点明细 —— 流程图各节点的详细说明：逐条列出判断条件、判断方式、查询方式与对应接口

2.2　角色权限表

同一份 Skill，不同角色拿到的权限范围、额度与升级路径各不相同

两张图共同构成 Skill 的两个层面：流程图层解决判定统一（同一订单不同角色结论一致），角色权限层解决职责边界（同一 case 只有一个角色负责，升级路径唯一）。角色差异不进 Skill 主体，由权限表独立承载——增删角色不影响判定逻辑。

各团队的收益落点

同一个团队，同样的工作步骤——但操作的对象和执行的方式彻底变了。图中横条为工作步骤数的对比。

🤖 智能客服
现在
从知识库提炼 QA 与客诉任务流 → 理解用户意图 → 匹配 QA 或任务流给出答复。
痛点：知识更新不及时、无法处理复杂判断
退费场景的现在：判断条件散在多张表、非常规订单靠穷举名单。
沉淀后
理解用户意图 → 按意图执行对应 Skill 给出答复。不再匹配碎片 QA，直接执行 Skill 流程
收益：退费答复有了统一判据，且判据本身带查询接口——不再受「知识更新不及时」影响；10 类订单 × 多条件的复杂判断从「答不了」变成「按流程走」。
现在3 步
沉淀后2 步
🎧 一线客服
现在
理解诉求 → 知识库找知识点 → 逐条判断确认 → 确认方案 → 可解决执行 / 不可解决转二线。
痛点：流程改动频繁、知识点分散、内容多易泄露
退费场景的现在：要自行到工作台 / 支付中心 / 哪吒 / 电商后台等系统核对订单类型，再翻对应知识点。
沉淀后
理解诉求 → 执行 Skill（一线权限版）；可解决直接处理，不可解决按 Skill 记录信息转二线
收益：① 不再翻知识库、不再跨系统找入口；② 信息收集标准化——转给二线的是一份结构化记录，而不是一段描述；③ 承接范围明确（低风险含「高期望」），不必再猜该不该转。
现在5 步
沉淀后2 步
🔧 二线客服
现在
理解诉求 → 知识库找知识点、确认一线处理节点 → 继续判断 → 可解决执行 / 不可解决转业务方 → 同步方案。
痛点：人力不足无法全量回电、业务方等待耗时、一线描述不清无从下手
退费场景的现在：6 类订单客服本无判断条件、只能升级反馈；播放记录超 3 年需另行发起云服务工单导出。
沉淀后
继续执行 Skill（二线权限版）；不可解决时等待业务方答复，再同步方案给用户
收益：① 结构化工单直接判断，不必重复核一线已走过的节点；② 聚焦区间明确（仅中风险）——把精力放在工单完结与电话善后；③ 规则外 case 有标准升级路径，不再靠个人经验兜底。
现在5 步
沉淀后3 步
🔍 质检
现在
查看样本对话 → 匹配知识点逐条对照判定 → 核验工单完整性 → 综合评估 / 申诉 / 闭环。
痛点：环节多且更新频繁、全量质检做不到、纯肉眼判定效率低
退费场景的现在：判定条件散在多张表与非常规订单穷举名单中，需逐条人工比对。
沉淀后
智能总结对话 → 核验 Skill 选择是否正确 → 人工复核提交 → 样本价值分析与数据监控闭环
收益：从「逐条知识检查」→「Skill 定位 + 规则执行 + 闭环」。判定条件全部是可核验字段（订单接口 / 发票状态 / 播放记录 / 历史退单），质检不再依赖肉眼比对知识点——这是「抽样 → 全量」能够成立的前提。
现在6 步
沉淀后3 步
📋 业务管理
现在
接收新业务知识 → 按客服阅读习惯转化为知识点 → 同步各使用者 → 接受修改需求再更新再同步。
痛点：流程调整来源众多、知识库无法同时满足人和机器人的需求
退费场景的现在：退费规则散在正文 6 章 + 多张表 + 2 个独立知识库条目；非常规订单靠维护一份穷举名单。
沉淀后
接收新业务知识 → 转化为 Skill 流程，系统自动新增 → 优化 Skill 流程
收益：从「维护散落文档」→「维护 Skill 流程」。变更有明确锚点、影响范围清晰；同时一份 Skill 同时服务人与机器人，不用再维护两套。
现在5 步
沉淀后3 步
📚 培训
现在
制作高频客诉场景课件 → 培训 / 跟听 / 试接 → 业务更新后人肉捕获调整点再更新课件。
痛点：课件更新滞后、流程复杂新手周期长
退费场景的现在：覆盖 10 类订单、3 类判定梯度与非常规订单穷举名单。
沉淀后
培训新人如何选择 Skill
收益：一个 Skill 一个模块、随沉淀同步产出——课件不再滞后于业务变更；新人按 Skill 指引即可走完退费判定，上手路径从「背知识点」变成「会选 Skill」。
现在3 步
沉淀后1 步
⚙️ 系统规划
现在
查看各业务线需求详情 → 评估需求与收益 → 规划排期 / 打回 → 产品设计 / 开发 / 交付 / 监测。
痛点：业务逻辑分散、改动影响多项目需分别修改、同需求不同线逻辑不同
退费场景的现在：订单类型判断分散在多个系统、是否已对接乐客参差不齐。
沉淀后
直接引用 Skill，无需重复开发
收益：Skill 作为统一底座，业务变更只需改 Skill，各项目自动同步——从「每个需求重新实现一遍退费逻辑」变成「引用同一份判定流程」。退费跑通的这套模板（触发 + 处理规则 + 角色行为层）可直接复用于开票、故障。
现在7 步
沉淀后1 步
